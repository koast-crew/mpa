# 로그인 / 동적 권한 관리 — 상세 설계 및 Claude Code 프롬프트 가이드

- **목적**: 다른 프로젝트에서 동적 ROLE 기반 Spring Security를 처음부터 구현하기 위한 가이드
- **개발 도구**: Claude Code
- **방식**: 아래 프롬프트를 순서대로 Claude Code에 입력해 단계별로 개발

---

## 이 구조가 일반 Spring Security와 다른 점

Spring Security 기본 구조는 ROLE을 코드에 하드코딩한다.

```
일반 방식:
  .hasRole("ADMIN")           ← 코드에 직접 박힘
  @PreAuthorize("hasRole('ADMIN')")

이 구조:
  ROLE을 DB 테이블에서 관리
  사용자 그룹에 ROLE을 N:M으로 할당
  로그인 시 DB에서 읽어 Spring Security GrantedAuthority로 변환
  → ROLE 추가/변경이 코드 수정 없이 DB에서 가능
```

Spring Security에서 확장이 필요한 포인트:

| 확장 포인트 | 기본 동작 | 이 구조에서 하는 것 |
|-------------|-----------|---------------------|
| `UsernamePasswordAuthenticationFilter` | form-encoded body 파싱 | JSON body 파싱으로 교체 |
| `AuthenticationProvider` | DaoAuthenticationProvider 사용 | 직접 구현 (정책 체크 포함) |
| `UserDetailsService` | DB에서 사용자 로드 | 사용자+그룹+ROLE 한 번에 로드 |
| `UserDetails` | 기본 구현체 사용 | 동적 ROLE → GrantedAuthority 변환 |
| `AuthenticationSuccessHandler` | 리다이렉트 | JSON 응답 + 세션 저장 |
| `AuthenticationFailureHandler` | 리다이렉트 | JSON 오류 응답 |
| `AuthenticationEntryPoint` | 로그인 페이지 리다이렉트 | HTTP 401 JSON 응답 |
| `AccessDeniedHandler` | 403 페이지 | HTTP 403 JSON 응답 |

## 개발 순서 개요

```
[1단계] DB 설계        → role, user_group, user_group_role 테이블
[2단계] 도메인 모델    → Role, UserGroup, User 엔티티 + RoleKey enum
[3단계] 데이터 접근    → Repository + MyBatis XML (user+group+roles 조인 쿼리)
[4단계] Security 확장  → Filter, Provider, UserDetails, UserDetailsService, UserPrincipal
[5단계] 응답 처리      → SuccessHandler, FailureHandler, EntryPoint, AccessDeniedHandler
[6단계] 설정 연결      → SecurityConfig에서 전체 조립
[7단계] 로그인 정책    → Policy 테이블 + 비밀번호 만료, 계정 잠금, 실패 횟수 제한
```

## 프롬프트 1 — DB 스키마 설계

> **목적**: 동적 ROLE 관리에 필요한 테이블 구조 설계

```
Spring Boot + MyBatis + PostgreSQL 프로젝트에서
동적 ROLE 기반 인증을 구현하려고 한다.

다음 조건에 맞는 DDL을 작성해줘.

[테이블 구성]
1. role
   - ROLE을 DB에서 관리하는 테이블
   - 컬럼: role_id(PK), role_name(Spring Security authority로 사용), role_key(enum 연결용), 
           role_target(어떤 앱 대상인지 구분, 예: ADMIN/USER), role_type(업무 유형),
           basic(기본 ROLE 여부), available(사용 여부), description, created_date

2. user_group
   - 사용자를 그룹으로 묶어 ROLE을 일괄 부여하기 위한 테이블
   - 컬럼: user_group_id(PK), user_group_name, available, description, created_date, modified_date

3. user_group_role
   - user_group과 role의 N:M 연결 테이블
   - 컬럼: user_group_role_id(PK), user_group_id(FK), role_id(FK)

4. user_info
   - 사용자 정보. user_group에 소속됨
   - 컬럼: user_id(PK, VARCHAR), user_group_id(FK), user_name, password(BCrypt 해시),
           status(ACTIVE/DISABLED/LOCKED/DORMANT/EXPIRED/DELETED/TEMP_PASSWORD/PENDING_APPROVAL),
           fail_login_count, last_login_date, last_password_change_date,
           email, created_date, modified_date

[관계]
- user_info N:1 user_group
- user_group N:M role (user_group_role 경유)
```

## 프롬프트 3 — Repository 및 MyBatis XML (핵심 조인 쿼리)

> **목적**: 로그인 시 사용자+그룹+ROLE을 한 번에 로드하는 쿼리 작성
>
> **핵심 포인트**: 이 쿼리 결과로 Spring Security의 `getAuthorities()`에서 ROLE 목록이 결정된다.

```
Spring Boot + MyBatis 프로젝트에서 사용자 인증에 필요한 Repository와 
MyBatis XML을 작성해줘.

[UserRepository 인터페이스]
메서드:
1. Optional<User> findUserWithGroupAndRoles(String userId)
   - user_info JOIN user_group LEFT JOIN user_group_role LEFT JOIN role
   - User 엔티티에 userGroup이 채워지고, userGroup.roles에 role 목록이 채워져야 함
   - Spring Security 인증 시 이 메서드로 권한을 로드함

[MyBatis XML — resultMap 설계]
- User를 최상위로, 그 안에 userGroup association, userGroup 안에 roles collection으로 중첩 매핑
- 중첩 resultMap 구조:
    User
      └─ userGroup (association)
              └─ roles (collection)  ← 이 목록이 getAuthorities()의 원천

[주의사항]
- role이 없는 사용자도 조회 가능해야 함 (LEFT JOIN)
- MyBatis typeAlias를 사용해 XML에서 클래스명 단순화
- resultMap의 id/result column명은 SQL 쿼리의 컬럼 alias와 정확히 일치해야 함
```

## 프롬프트 4 — Spring Security 핵심 클래스 구현

> **목적**: Spring Security의 인증 흐름을 JSON 기반 + 동적 ROLE로 확장
>
> **Spring Security 확장 포인트 설명**:
> - `UsernamePasswordAuthenticationFilter` → JSON body를 읽기 위해 상속 오버라이드
> - `UserDetailsService` → 사용자를 DB에서 로드하는 표준 인터페이스
> - `UserDetails` → Spring Security가 인식하는 사용자 정보 포맷. `getAuthorities()`가 ROLE 목록 반환
> - `AuthenticationProvider` → 실제 인증 로직 담당. 비밀번호 검증, 계정 상태 확인

```
Spring Boot 3.x + Spring Security 프로젝트에서 JSON 기반 로그인과 
동적 ROLE 인증을 위한 Security 클래스를 작성해줘.
패키지명: [패키지명].security

[1] JsonUsernamePasswordAuthenticationFilter
    - UsernamePasswordAuthenticationFilter를 상속
    - attemptAuthentication() 오버라이드
    - 요청 Content-Type이 application/json인지 확인
    - request body를 ObjectMapper로 파싱해 username, password 추출
    - UsernamePasswordAuthenticationToken 생성 후 AuthenticationManager에 위임

[2] CustomUserDetails (UserDetails 구현체)
    - UserDetails를 구현
    - User 엔티티를 생성자로 받음
    - getAuthorities(): user.getUserGroup().getRoles()를 순회해 
      role.getRoleName() → SimpleGrantedAuthority로 변환해 반환
      → 이 메서드가 동적 ROLE의 핵심
    - getPassword(): user.getPassword() 반환
    - getUsername(): user.getUserId() 반환
    - isAccountNonExpired(), isAccountNonLocked(), isCredentialsNonExpired(), isEnabled(): 모두 true 반환
      (계정 상태 검증은 CustomAuthenticationProvider에서 별도 처리)

[3] CustomUserDetailsService (UserDetailsService 구현체)
    - UserDetailsService 구현
    - loadUserByUsername(String userId) 
      → UserRepository.findUserWithGroupAndRoles(userId)로 User 로드
      → 없으면 UsernameNotFoundException
      → CustomUserDetails 반환

[4] UserPrincipal (세션 저장 객체)
    - UserDetails와 Serializable 구현
    - 세션에 저장될 인증된 사용자 정보를 담는 객체
    - 필드: userId, userName, userGroupId, userGroupName, password, status(UserStatus enum),
            failLoginCount, lastLoginLockOver, passwordChangeTermOver, lastLoginDate,
            loginIp(세션 하이재킹 방지용), authorities(Collection<GrantedAuthority>)
    - @Builder 적용
    - UserDetails 메서드: getAuthorities()는 authorities 필드 반환
    - isAccountNonExpired(), isAccountNonLocked(), isCredentialsNonExpired(), isEnabled()는
      status 필드와 조건 필드를 조합해 정확히 구현
      예) isEnabled(): status == ACTIVE || status == TEMP_PASSWORD

[5] CustomAuthenticationProvider (AuthenticationProvider 구현체)
    - AuthenticationProvider 구현
    - 의존성: BCryptPasswordEncoder, CustomUserDetailsService
    - authenticate() 처리 순서:
      1) customUserDetailsService.loadUserByUsername(userId) 호출
      2) BCryptPasswordEncoder.matches(입력비밀번호, DB해시비밀번호) 검증 → 불일치 시 BadCredentialsException
      3) 계정 상태 확인 (ACTIVE 또는 TEMP_PASSWORD만 통과) → 그 외 BadCredentialsException
      4) 비밀번호 변경 필요 여부 확인 (TEMP_PASSWORD → 별도 처리)
      5) 인증 성공 시 UserPrincipal 빌드 (authorities는 userDetails.getAuthorities() 사용)
      6) UsernamePasswordAuthenticationToken(userPrincipal, null, userPrincipal.getAuthorities()) 반환
    - supports(): UsernamePasswordAuthenticationToken.class.isAssignableFrom(authentication)
```

## 프롬프트 5 — 응답 처리 핸들러 4종

> **목적**: Spring Security의 기본 리다이렉트 방식을 REST API용 JSON 응답으로 교체

```
Spring Security에서 인증 결과를 JSON으로 응답하는 핸들러 4개를 작성해줘.
모든 응답은 아래 ApiResponse 포맷을 사용한다.

[공통 응답 포맷]
ApiResponse<T> {
    T payload;
    Object pagination;
    Exception exception;  // 오류 시에만 채움
}

[1] CustomAuthenticationSuccessHandler (AuthenticationSuccessHandler 구현)
    - 로그인 성공 시 호출
    - authentication.getPrincipal()을 UserPrincipal로 캐스팅
    - 세션에 "USER_SESSION" 키로 UserPrincipal 저장
    - HTTP 200 + ApiResponse(payload: userPrincipal) JSON 응답

[2] CustomAuthenticationFailureHandler (AuthenticationFailureHandler 구현)
    - 로그인 실패 시 호출 (비밀번호 틀림, 계정 잠금 등 모든 AuthenticationException)
    - HTTP 401 + ApiResponse(exception: 오류 정보) JSON 응답
    - exception.getMessage()를 오류 메시지로 사용

[3] CustomAuthenticationEntryPoint (AuthenticationEntryPoint 구현)
    - 인증 없이 보호된 URL에 접근했을 때 호출
    - HTTP 401 + ApiResponse(exception: "인증이 필요합니다.") JSON 응답

[4] CustomAccessDeniedHandler (AccessDeniedHandler 구현)
    - 인증은 됐으나 권한이 없는 URL에 접근했을 때 호출
    - HTTP 403 + ApiResponse(exception: "권한이 없습니다.") JSON 응답

[공통 조건]
- response.setContentType("application/json;charset=UTF-8")
- ObjectMapper는 생성자 주입으로 받음 (@Bean으로 등록된 것 사용)
- @Component, @RequiredArgsConstructor, @Slf4j 적용
```

## 프롬프트 6 — SecurityConfig 조립

> **목적**: 지금까지 만든 클래스들을 Spring Security 필터 체인에 연결

```
Spring Boot 3.x Spring Security에서 아래 구성으로 SecurityFilterChain을 작성해줘.

[필터 체인 구성]
1. JsonUsernamePasswordAuthenticationFilter 등록
   - 처리 URL: /login/process
   - AuthenticationManager 연결
   - 성공 핸들러: CustomAuthenticationSuccessHandler
   - 실패 핸들러: CustomAuthenticationFailureHandler

2. 예외 처리 등록
   - authenticationEntryPoint: CustomAuthenticationEntryPoint
   - accessDeniedHandler: CustomAccessDeniedHandler

3. URL 권한 규칙
   - /login/** 는 누구나 접근 가능 (permitAll)
   - 나머지 모든 요청은 RoleKey.ADMIN_LOGIN 권한 필요
     .anyRequest().hasAuthority(RoleKey.ADMIN_LOGIN.name())

4. 세션 관리
   - 동시 접속 1명으로 제한 (.maximumSessions(1))

5. CSRF 비활성화
   - REST API 구조이므로 csrf 비활성화

6. BCryptPasswordEncoder @Bean 등록
   - SecurityConfig 내에 @Bean으로 등록
   - CustomAuthenticationProvider에서 주입받아 사용

[주의사항]
- addFilterAt()으로 JsonFilter를 UsernamePasswordAuthenticationFilter 위치에 등록
- AuthenticationManager는 AuthenticationConfiguration에서 가져옴
```

## 프롬프트 7 — 로그인 정책 기능 추가

> **목적**: 비밀번호 만료, 계정 잠금, 로그인 실패 횟수 제한을 DB 정책으로 관리
>
> **이 기능이 필요한 이유**: ROLE 권한 관리와 마찬가지로, 보안 정책도 하드코딩이 아닌 DB에서 관리해 운영 중 변경 가능하게 함

```
Spring Boot + MyBatis 프로젝트에서 로그인 정책 기능을 구현해줘.

[policy 테이블 설계]
- password_change_term: 비밀번호 변경 주기 (일수)
- user_fail_login_count: 최대 로그인 실패 횟수 (초과 시 계정 잠금)
- user_last_login_lock: 마지막 로그인 후 잠금 기간 (일수, 장기 미접속 잠금)
- user_duplication_login: 중복 로그인 허용 여부 (boolean)
- security_session_timeout_enabled: 세션 타임아웃 적용 여부
- security_session_timeout: 세션 타임아웃 시간 (분)

[Policy 엔티티 + PolicyRepository + PolicyMapper XML]
- PolicyRepository.findLatest(): 가장 최근 정책 1건 조회

[PolicyService]
- getLatest(): 현재 적용 중인 정책 반환

[CustomAuthenticationProvider에 정책 반영]
authenticate() 메서드에서 PolicyService로 정책을 읽어 다음을 처리:
1. 비밀번호 만료 체크
   - user_info.last_password_change_date + policy.password_change_term 비교
   - 만료 시 로그인은 허용하되 비밀번호 변경 필요 플래그 처리
2. 로그인 실패 횟수 초과 체크
   - user_info.fail_login_count >= policy.user_fail_login_count → 계정 잠금 처리
   - 비밀번호 틀릴 때마다 fail_login_count 증가 후 DB 업데이트
   - 로그인 성공 시 fail_login_count = 0 으로 초기화
3. 장기 미접속 잠금 체크
   - user_info.last_login_date + policy.user_last_login_lock 비교
   - 초과 시 접근 거부
4. 세션 타임아웃 적용
   - security_session_timeout_enabled = true 이면 session.setMaxInactiveInterval() 적용
```

## 프롬프트 8 — 테스트

> **목적**: 구현된 인증 흐름이 정상 동작하는지 검증

```
구현된 Spring Security 동적 ROLE 인증에 대한 테스트를 작성해줘.

[테스트 시나리오]
1. 정상 로그인
   - POST /login/process, Content-Type: application/json
   - body: { "username": "test_admin", "password": "password123" }
   - 기대 결과: HTTP 200, response body에 userId, userGroupName 포함

2. 비밀번호 틀림
   - 잘못된 password 입력
   - 기대 결과: HTTP 401

3. ADMIN_LOGIN 권한 없는 사용자 로그인 시도
   - user_group에 ADMIN_LOGIN role이 없는 사용자
   - 기대 결과: 로그인은 성공(HTTP 200)하지만 이후 API 요청 시 HTTP 403

4. 로그인 없이 보호된 URL 접근
   - GET /api/users (로그인 없이)
   - 기대 결과: HTTP 401

5. 로그인 실패 횟수 초과 → 계정 잠금
   - 정책상 최대 실패 횟수만큼 틀린 비밀번호 입력
   - 다음 시도에서 계정 잠금 오류 반환
```

## 전체 개발 흐름 요약

```

    ↓

    ↓

    ↓

            ├── JsonUsernamePasswordAuthenticationFilter  (JSON 로그인)

            ├── CustomUserDetailsService                  (DB 로드)
            ├── UserPrincipal                             (세션 객체)
            └── CustomAuthenticationProvider             (인증 로직)
    ↓
프롬프트 5: 응답 처리 핸들러 4종
            ├── SuccessHandler   (로그인 성공 → JSON 응답)
            ├── FailureHandler   (로그인 실패 → 401)
            ├── EntryPoint       (미인증 접근 → 401)
            └── AccessDeniedHandler (권한 없음 → 403)
    ↓
프롬프트 6: SecurityConfig (전체 조립)
    ↓
프롬프트 7: 로그인 정책 (비밀번호 만료, 계정 잠금)
    ↓
프롬프트 8: 테스트
```

## 각 프롬프트 실행 전 체크리스트

프롬프트를 실행하기 전에 `[패키지명]`, `[ROLE 목록]` 등 프로젝트에 맞는 값으로 교체한다.

| 항목 | 교체 내용 |
|------|-----------|
| `[패키지명]` | 프로젝트 기본 패키지 (예: `com.example.myapp`) |
| `[ROLE 목록]` | 프로젝트에 필요한 ROLE enum 값 목록 |
| `RoleKey.ADMIN_LOGIN` | 이 프로젝트의 기본 접근 권한 ROLE 키 |
| 테이블명 | 프로젝트 DB 네이밍 규칙에 맞게 조정 |
